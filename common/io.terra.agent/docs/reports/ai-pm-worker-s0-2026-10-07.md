## 7. 해석과 한계

**판정: Q-12 미달. 계획을 멈추고 설계를 다시 본다.** 이 결과는 좋게 보이도록 손대지 않았다. 작업·수용 테스트는 그대로이고 실패한 실행도 그대로 센다. 사람 개입은 0이다.

**읽을 수 있는 것**

- 가장 큰 사실은 A가 20/20을 완료단가 $0.067에 끝냈다는 것이다. B·C가 이길 여지가 거의 없는 기준선이다.
- 워커 비용은 결론을 바꾸지 못한다. 워커 단가를 0으로 두어도 완료 작업당 PM 비용만으로 C는 $0.222, B는 $0.605로 A($0.067)의 3.3배·9배다. 워커 단가를 GPU 임대 수준($1/시간)으로 올리면 C $0.385, B $0.985로 더 벌어진다.
- 원인은 PM의 일이 줄지 않고 늘어난다는 점이다. 실행당 PM 비용은 A $0.067, B $0.151, C $0.156이다. PM이 지시문을 쓰고 결과를 검토하는 비용이 PM이 직접 고치는 비용보다 크다. 이 작업 크기에서는 위임이 PM 일을 덜지 못한다.
- B의 실패 15건 중 14건, C의 실패 6건 중 4건이 위임 상한(6회)까지 쓰고 끝났다. 소형 모델이 같은 지점에서 되풀이해 막힌다. 워커 시간 초과와 비정상 종료는 0건이다.
- 소형 모델은 실제로 파일을 고친다(C 14/20). 문제는 도구 사슬이 아니라 고치는 품질과 PM이 그것을 바로잡는 비용이다.

**결론을 약하게 하는 것 — 이 실험이 보여 주지 못하는 것**

1. **PM이 Sonnet이다.** 계획의 "대형 모델"은 Opus급을 가정하지만, 구독 한도를 고려해 이번 본 실험은 Sonnet으로 돌렸다. A도 같은 Sonnet이라 비교는 서지만 "대형 PM"의 시험은 아니다. 같은 T1 여섯 작업에서 파일럿(Opus PM)의 C는 6/6, 본 실험(Sonnet PM)의 C는 3/6이다. PM 모델이 위임 품질을 좌우할 가능성이 있으나 반복이 1회라 편차와 구분하지 못한다.
2. **반복 1회, 표본 작음.** 작업당 r1뿐이다. 같은 작업이 파일럿과 본 실험에서 갈린 경우가 있다(go-t1-parsebool의 B, go-t1-urljoin의 C 등). 등급별 비율(T1 3/6 대 T2 8/8)은 잡음으로 읽어야 한다.
3. **작업이 쉽다.** A가 20/20이므로 위임이 이득을 낼 수 있는 어려운 작업 구간이 측정되지 않았다. "A가 못 푸는 일을 B·C가 푸는가"는 이 세트로 알 수 없다.
4. **B는 toolshim이다.** `qwen2.5-coder:7b`가 Ollama에서 도구 호출을 텍스트로 내놓아(`tool_calls` 없음) Goose의 toolshim으로 돌렸다. B의 낮은 완료율(5/20)이 모델 탓인지 Goose + toolshim 층 탓인지 가르지 못했다. 같은 모델의 C(14/20)가 훨씬 낫다는 점이 층 탓을 시사하지만 검증하지 않았다.
5. **모델 하나.** 7B 한 종만 돌렸다. `qwen3:8b` 등 네이티브 도구 호출 모델이나 더 큰 워커(`qwen3-coder:30b`)는 시험하지 않았다.

**키트에서 고친 것(커밋 포함):** Windows cp932 디코딩, Goose toolshim 설정, 끊긴 실행 폴더 삭제(읽기 전용 `.git`). 실행 중 PC 재시작과 Docker 소켓 문제로 여러 번 중단됐고, 중단된 실행은 처음부터 다시 돌렸다.

## 읽는 법

- 완료 = 숨긴 수용 테스트와 기존 테스트가 모두 통과. 지시문에 적힌 행동만 테스트한다.
- PM 비용은 Claude Code가 보고한 `total_cost_usd`다. 구독으로 돌렸어도 API 단가로 환산된 값이다.
- 워커 비용은 워커 실행 시간 × 설정한 시간 단가다. 전기료 기준이면 낮고, GPU 임대 기준이면 높다 — 둘 다 넣어 보고 결론이 바뀌는지 본다.
- 사람 개입은 S0에서 0으로 고정된다. 사람이 손댄 실행은 지우고 다시 돌린다.
